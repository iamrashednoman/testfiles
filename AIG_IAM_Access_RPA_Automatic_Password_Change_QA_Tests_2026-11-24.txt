=====================================================================
 1  READ FIRST
=====================================================================
 * The bot signs in to Fujitsu Mainframe with its own service account.
   The host expires that password after 90 days.
 * Every hour the bot checks the age of the password. When it is old:
     change automatically = Off : the bot e-mails reminders only.
     change automatically = On  : the bot changes the password itself
                                  on Task 0890.
 * Tests 1-4 and the e-mail tests E1-E4 never change the password.
 * Test 5 changes the REAL password. Run it on a single-server QA
   environment only:
     - The settings are shared by every server on the same database.
     - The new password is saved only in the Windows Credentials of
       the server that changed it.
     - Another server would keep the old password, its sign-ins would
       be refused, and the account could be locked.
 * In production keep "change automatically" Off unless only one
   server processes Fujitsu Mainframe.
 * Never leave "change after" = 1 saved with "change automatically"
   On. The next hourly check would change the real password.


=====================================================================
 2  WORDS USED
=====================================================================
 Age        Days since the last change, counted in Japan time (JST).
 Last change date
            The LATER of: the bot's own record of its last change,
            and the date typed in "last changed on".
 OK         Young password. Nothing happens.
 Due        Age >= "change after".
 Urgent     Days left <= "urgent e-mail" days, and more than 0.
 Expired    0 days left or fewer. The bot never changes an expired
            password.
 Check      The hourly look at the age. "Check password age now"
            runs the same check at once.
 Try        One real change on Task 0890. At most one try a day.

 With the default settings:
   day 0-79   OK       nothing happens
   day 80-84  Due      reminder e-mail (Off) or automatic change (On)
   day 85-89  Urgent   urgent e-mail every day while not changed
   day 90+    Expired  expired e-mail every day, no change tried

   * Age line under the Tests buttons, e.g.

       password_rotated            each automatic try
       service_password_changed    each change on Task 0890

 Known limits of the age line today:
   * It does not show the urgent date.
   * It does not say "expired". It shows "0 days left" or a
     negative number instead.
   * It does not show when "change after" was replaced.
 Work out these values by hand with section 6.

 6  VALUES FOR EACH TEST
=====================================================================
 Read the age N (days) from the age line today. N must be 1 or more.
 Keep "last changed on" EMPTY. An older date there changes nothing
 once the bot has changed the password itself.

 Test                          change auto  expires after  change after  urgent
 ----------------------------  -----------  -------------  ------------  ------
 Test 1  Due reminder          Off          empty (90)     1             5
 Test 2  Urgent e-mail         Off          N + 3          1             5
 Test 3  Expired               Off          N              1             any
 Test 4  Blocked by pause      On           empty (90)     1             5
 Test 5  Real automatic change On           empty (90)     1             5
 E3      Urgent with reason    On           N + 3          1             5

 Example: the age line says "4 days ago", so N = 4.
   Test 2: expires after 7 -> 3 days left -> urgent.
   Test 3: expires after 4 -> 0 days left -> expired.

 If N is 90 or more, use expires after N + 30 instead of empty for
 Tests 1, 4 and 5.

 Every test uses the same four moves:
   1. Type the values (section 3 location).
   2. Save changes.
   3. Tests > Check password age now.
   4. Wait about 10 seconds, then read the result message and the
      age line.


=====================================================================
 7  TESTS 1-6
=====================================================================
 TEST 1  Reminder when the change is due (no change)
 ----------------------------------------------------
 Do      : Off, expires empty, change after 1, urgent 5 > Save >
           Check password age now.
 Expect  : "Password age check: change due; a reminder was e-mailed."
           Age line: N days ago, (90 - N) days left.
           E-mail E1 "... service-account password change due".

 TEST 2  Urgent e-mail
 ---------------------
 Do      : Off, expires after N + 3, change after 1, urgent 5 > Save >
           Check password age now.
 Expect  : Age line "(3 days left)".
           Result "change due; a reminder was e-mailed".
           E-mail E2 "URGENT: ... expires soon",
           "The password expires in 3 day(s)."
 If not  : urgent must not be 0, expires after must be larger than N,
           and change automatically must be Off. With it On, the bot
           tries to change the password instead.

 TEST 3  Expired
 ---------------
 Do      : Off, expires after N (or less), change after 1 > Save >
           Check password age now.
 Expect  : "Password age check: the password has expired."
           E-mail E4 "URGENT: ... has expired". No change is tried,
           even with change automatically On. The real password is
           not affected: only the bot's count is.

 TEST 4  Blocked while processing is paused (safe, no change)
 ------------------------------------------------------------
 Do      : System > Pause processing. Then On, expires empty,
           change after 1 > Save > Check password age now.
 Expect  : "Password age check: the change could not start now
           (see the log)."
           Log: "Automatic password change of Fujitsu Mainframe not
           started: processing is paused by an administrator".
           No e-mail (the password is due, not urgent).
 After   : If you stop here, set change automatically back to Off
           and Save straight away.

 TEST 5  The real automatic change (single-server QA only)
 ----------------------------------------------------------
 Needs   : 06:00-22:00 JST, no password change by the bot in the
           last 24 hours, no request running, the password safe open.
 Do      : Keep the Test 4 values (On, change after 1).
           System > Resume processing.
           Settings > Check password age now.
           Do not type in the FINESIII window.
 Expect while it runs (3 to 6 minutes):
           System shows processing paused by "Automatic password
           change"; the bot opens Task 0890.
 Expect afterwards:
           "Password age check: the password was changed."
           Age line "(0 days ago)", 90 days left.
           Processing running again.
           Audit: service_password_changed (outcome changed, how
           automatic, actor "Automatic password change") and
           password_rotated (changed).
           Log: "Automatic password change of Fujitsu Mainframe: the
           password is N days old", then Task 0890 正常終了.
           E-mail E5 "... service-account password changed",
           How: "Changed automatically by the bot, based on the
           password's age". No password in the e-mail.
           Evidence: a new terminal-check-... folder, with the
           password area blacked out.
 Then    : Tests > Test sign-in and navigation. Expect: passed.
 If not  : "the change was refused by the host": the old password
           stays, failures 1, e-mail E7 "... not changed".

 TEST 6  Only one try a day
 --------------------------
 Do      : Right after Test 5, Check password age now again.
 Expect  : After a change: "not due yet, nothing to do" (age 0).
           After a refusal: "already tried today". No second sign-in.

 AFTER TEST 5: NOBODY KNOWS THE PASSWORD
   The bot chose it and keeps it only on this server. To set a known
   one, wait 24 hours, then:
     System > Pause processing >
     Settings > Fujitsu Mainframe terminal > Change service-account
     password > leave "Current password" EMPTY (a Developer may) >
     type the new password twice > Change password > OK.
   Expect "Password changed (正常終了)" and audit
   service_password_current_from_store. Save the new password in the
   password safe, then System > Resume processing.

 How to trigger each one (values from section 6):
   E1  QA server. Test 1. A second click the same day: no second
       e-mail.
   E2  QA server. Test 2.
   E1  again: right after E2, set expires after back to empty and
       check again. E1 is sent a second time the same day, because
       the kind changed.
   E3  QA server, safe. System > Pause processing. On, expires after
       N + 3, change after 1, urgent 5 > Save > Check password age
       now. Expect E3 with "processing is paused by an
       administrator". No change is tried. Do E3 on a day without
       E2, or E2 blocks it. Set change automatically back to Off
       afterwards.
   E4  QA server. Test 3.
   E5  Single-server QA. Test 5.
   E6  QA server, 24 hours after a change. Pause processing >
       Change service-account password > a new password twice.
   E7  Lab only (simulated host). A real host can't be made to
       refuse a new password on purpose.
   E8  Lab only. Right after E7, set "stop after failed tries" to 1
       and Check password age now.

 The once-a-day rule (E1-E4, E8):
   The bot keeps only the LAST notice it sent (day and kind).
     due, due               -> 1 e-mail
     due, urgent, due       -> 3 e-mails
   A successful change clears it. The console result still says "a
   reminder was e-mailed" when nothing was sent, so judge by the
   inbox.

 No e-mail is sent (by design today) when:
   * the password is due, change automatically is On, and the change
     can't start: the reason is in the log only;
   * a try stopped before the new password was sent (for example
     row 102 empty, or a sign-in failure). Failures still go up, and
     E8 follows at the limit;
   * the result could not be confirmed: the new password is kept
     pending until the next console change checks it;
   * the same kind of age e-mail was already sent today.

 Check in each e-mail:
   [ ] Subject as above, with the system name and environment label.

   [ ] Status banner and detail rows filled in. Age e-mails: last

   [ ] Dates match the age line.
   [ ] No password anywhere.
   [ ] To/CC hold the three groups above.
   [ ] Audit trail shows the e-mail as sent.

=====================================================================
 10  ANSWERS TO COMMON QUESTIONS
=====================================================================
 Q1  What is the point of urgent e-mails if the password is changed
     on day 80?
     The urgent e-mail is the safety net for when the change on day
     80 does NOT happen. If the change works, the age goes back to 0
     and no urgent e-mail is ever sent.
       * Off (the default): due e-mails from day 80, urgent e-mails
         from day 85.
       * On, change can't start on days 80-84 (outside hours,
         paused, host not ready, a request running): the reason is in
         the log only. From day 85 the urgent e-mail warns people,
         with the reason.
       * On, host refused: urgent e-mail on the day of the failed
         try.
       * On, stopped: the "stopped" e-mail replaces the urgent one.
     To warn people earlier while the bot is still trying, raise
     "urgent e-mail" (e.g. 10 = urgent from day 80).

 Q2  How does the bot check before changing, and how often a day?
     Five layers. If any check fails, nothing is changed:
       1  Hourly age check: Mainframe terminal set up, not CyberArk,
          last change known, due or urgent (not expired), change
          automatically On, not stopped, not tried today.
       2  Start conditions: credential store available, password
          kept there, no change by the bot in the last 24 hours,
          inside operating hours, host ready, processing not paused
          by a person.
       3  Just before signing in: new requests held (paused as
          "Automatic password change"), wait up to 30 minutes for a
          running request, terminal free, no scheduled sign-in check
          running, no recent failed sign-in, host answers on its port.
       4  New password: generated, then checked against the console
          rules (8 characters, letter first, letters and digits,
          allowed symbols only, not the current one, no staff code).
       5  On the host: an earlier pending password is decided first;
          the new one is kept as pending before submitting; sign in
          with the current password; Task 0890; row 102 must show
          the new password before 00; read 正常終了 or the host's
          reason.
     How often:
       Age check            every hour, 24 a day (first one 10 minutes
                            after the service starts), plus each
                            "Check password age now".
       Start conditions     at each hourly check until a try starts.
                            These checks don't sign in.
       Change try           at most 1 a day. A check that stopped
                            before signing in doesn't count.
       Sign-ins in one try  normally 1. Plus 1 if the result screen
                            can't be read. Plus 1 first if an earlier
                            change was left pending.
       Stop                 after 2 failed days in a row, or at once
                            when the current password is refused.
       Gap between changes  at least 24 hours.
